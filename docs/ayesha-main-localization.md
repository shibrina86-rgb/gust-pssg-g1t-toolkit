# Ayesha Switch main 한글 패치 재현 기록

이 문서는 2026-09-12 작업에서 관찰한 NSO 실행 파일의 문자열 패치 방법이다. 게임 실행 파일, 폰트, 번역 CSV 전체, 개인 경로는 포함하지 않는다. 다른 거스트 게임에 주소와 테이블 크기를 그대로 적용하지 않는다.

마지막 단계는 4,068개 기준본에 2,495개를 추가했다. 실행 확인은 사용자 보고이며, 모든 분기·화면·저장 데이터를 전수 검증했다는 뜻이 아니다. 새 작업은 가능한 한 마지막 정상본에서 시작한다.

분석용 일본판 main SHA-256: `3f3f0e95ca375595b069bfb3399e5349c24077ddab93a045cc5b96045fa835eb`.

영문판 build ID: `b9146e1cad9e36ba61c7dad612156f0466ebaad3000000000000000000000000`.
일본판 build ID: `381a6922e4f62b4e5ef189e7b0c77b1022902e6f000000000000000000000000`.
둘은 레이아웃이 다른 빌드다. 일본판은 대조 자료이고 최종 패치 대상은 기존 영문판이다.

## 세 가지 자료의 역할

1. **Switch 영문판**: 실제 패치 대상, 코드·참조·제어 토큰·수치의 기준.
2. **Switch 일본판**: 문자열 역할 및 테이블 구조를 비교하는 자료. 주소를 복사하는 기준이 아니다.
3. **로컬 PC 한글 패치와 원본 PC 실행 파일**: 대응하는 영어/일본어/한글 레코드와 기존 글리프 매핑을 찾는 자료. 사용 권한을 확보한 자료만 로컬에서 사용한다.

글자 의미, 문자열 인코딩, 글리프 슬롯, 문자열 참조를 각각 확인한다. 의미가 맞아도 폰트 매핑이나 포인터가 다르면 표시가 깨지거나 실행이 실패할 수 있다.

## 분해할 때의 순서

1. 원본과 정상본을 읽기 전용 보관하고 파일 해시, build ID, 압축 플래그를 기록한다.
2. NSO 헤더에서 text/rodata/data의 파일 위치, 메모리 위치, 압축 길이, 해제 길이, BSS를 각각 읽는다. 압축된 파일 자체를 문자열 검색 대상으로 삼지 않는다.
3. 각 세그먼트를 해제하고 메모리 주소 기반 참조 지도를 만든다. 파일 오프셋과 메모리 주소를 혼동하지 않는다.
4. 원래 바이트와 분석용 가상 메모리 복사본을 분리한다. 상대 재배치를 복사본에 적용해 실제 테이블 모습을 복원한다.
5. 주소별 문자열과 참조 위치를 수집한다. 링커가 문자열 접미부를 공유할 수 있으므로 유효한 포인터에서 시작하는 문자열은 앞 바이트가 NUL이 아니어도 존재할 수 있다.
6. 일본판은 같은 과정을 별도로 거친다. 인접 레코드, 숫자 필드, 레코드 간격, 표시명/설명 필드의 역할을 비교한다.

### 상대 재배치에서 얻은 교훈

이번 빌드에서는 24바이트 레코드의 `target / kind / addend` 형태와 `kind == 0x403`인 상대 재배치가 중요했다. 원래 data 슬롯은 0이어도 재배치 후에는 문자열 포인터가 된다. 이 기록에서 materialize한 레코드 수는 영문 239,950개, 일본판 255,778개였다.

이 수치는 파서 완전성의 보증이 아니다. 실제 재배치 구간과 레코드 형식을 확인해야 하며, rodata 전체에서 우연히 발견된 `0x403`을 전부 재배치라고 간주하면 안 된다. symbol/type 비트도 형식에 맞게 해석한다.

패치할 때는 분석용으로 materialize한 세그먼트를 통째로 저장하지 않는다. 승인된 표시 슬롯에 대응하는 **원본 재배치 addend**만 새 주소로 바꾼다. 실제 로더가 수행할 일을 이중 적용하지 않는다.

## 번역 대응표 만들기

- PC의 영어/한글 배열 간 거리는 테이블마다 다르며 부호도 다를 수 있다. 전역 델타 하나를 쓰지 않는다.
- 대응 후보는 같은 문자열뿐 아니라 인접 레코드와 필드 간격으로 뒷받침한다. 같은 영어가 서로 다른 한글에 대응하면 중립 번역 또는 참조별 번역을 검토한다.
- 일본판 테이블 매칭에서 포인터 값을 정규화하고 주변 숫자 필드를 비교할 수 있다. 그러나 포인터와 0만 반복되는 창, 거대한 동일 서명 묶음, 다른 언어 테이블은 오대응 위험이 크다.
- 좁은 창 매칭이나 주변 주소 델타는 후보 생성 수단이다. 그 자체가 의미 검증은 아니다. 카나가 없는 한자 문구를 제외하면 실제 메뉴가 누락되고, CJK 전체를 허용하면 중국어 배열과 섞일 수 있다.
- PC 원본과 PC 한글판도 레이아웃이 다를 수 있다. 양쪽에서 유일하게 대응하는 영어 앵커와 일관된 테이블 경계로 일본어→한글 연결을 확인한다.
- PC판의 수치가 Switch판과 다르면 현재 Switch 영문의 효과 수치·권장 레벨을 유지한다. 실제로 품질 증가량과 권장 레벨에 차이가 있었다.

예시 CSV 필드: `candidate_id, english_hex, korean, glyph_hex, source_build, source_table, original_address, approved_reference_slots, code_refs, evidence, status`.

## 한글을 저장하는 방법

이번 자료는 한글을 그대로 UTF-8로 넣는 방식만으로 해결되지 않았다. 기존 패치가 사용하는 한글→대체 코드포인트 매핑과 폰트의 글리프 슬롯이 일치해야 했다.

1. 권한이 있는 로컬 매핑을 읽고 한글 문자열을 글리프 문자열로 변환한다.
2. 매핑에 없는 한글을 검출한다. 원본 PC 번역에도 매핑 불가능한 오타가 있었으므로 원본이라는 이유만으로 통과시키지 않는다.
3. `%s`, `%d` 등 실제 포맷 인자의 형식·순서와 `<IM…>` 버튼 아이콘 ID를 유지한다. 일반 퍼센트 문장과 printf 인자를 구분한다.
4. `<CR>`과 실제 개행, CSV에 보이는 `\n`을 구분한다. 색상 토큰도 게임이 해석할 수 있는 형태로 유지한다.
5. 글리프 매핑은 신뢰할 수 없는 pickle을 일반 역직렬화해서 읽지 않는다. 실행 가능한 객체를 거부하는 데이터 전용 로더나 검증된 단순 형식을 쓴다.

관련 폰트 작업은 [G1N/폰트 기록](g1n-to-switch-font-workflow.md)을 별도로 읽는다.

## 참조를 바꾸는 방법

최종 확장 단계에서는 원본 영어 문자열 저장 영역을 보존하고 새 글리프 문자열을 기존 예약 풀에 추가했다. 같은 단어의 엔진 키까지 변하지 않도록 표시용 참조만 수정했다.

- 재배치: 승인된 표시 슬롯의 addend를 변경한다.
- 직접 포인터: 실제 포인터 필드임이 확인된 위치만 변경한다. 정수와 우연히 같은 비트열을 포인터로 취급하지 않는다.
- AArch64 코드: 확인된 `ADRP + ADD` 등의 참조를 해석하고 새 주소의 도달 범위를 검사한다. 페이지 레지스터가 다른 명령에서도 살아 있다면 단순한 페이지 교체는 금지한다.
- `ADR`의 도달 범위를 넘으면 명령을 억지로 패치하지 않는다. 별도 검증된 리다이렉션 방법이 필요하다.
- 기존 번역을 수정할 때는 영어 문자열이 보존되어 있어도 현재 포인터는 이미 새 풀을 향할 수 있다. manifest로 현재 참조를 추적하며 원본 주소가 그대로 남았다고 가정하지 않는다.

### 이 빌드에서 관찰한 값 — 다른 빌드에 복사 금지

| 항목 | 값 |
|---|---|
| 확장 기준 text 메모리 주소 / 길이 | `0` / 5,070,848 |
| rodata 메모리 주소 / 길이 | 5,070,848 / 8,815,896 |
| data 메모리 주소 / 길이 | 13,889,536 / 7,729,152 |
| 문자열 풀 시작 / 끝(미포함) | `0x141e000` / `0x149e000` |
| 예약 풀 용량 | 524,288바이트 |
| 4,068개 단계 사용량 | 320,112바이트 |
| 6,563개 단계 사용량 | 434,004바이트 |
| 일부 UI 레코드 간격 / 로케일 배열 간격 | `0x28` / `0x2bf68` |

기존 확장 기준본은 BSS를 materialize하고 BSS 헤더 크기를 0으로 설정한 형태였다. 이를 일반 NSO의 기본 상태로 오해하지 않는다. 새 게임에서 BSS/세그먼트 크기를 임의 변경하거나 같은 풀 주소를 쓰지 않는다. MOD0와 동적 정보, 섹션 간 관계를 보존한다.

이번 6,563개 빌드는 이미 마련된 풀 안에 들어가 추가 메모리 확장이 필요하지 않았다. serializer는 비압축 세그먼트와 해시 플래그, 각 파일 오프셋·길이·SHA-256을 실제 출력에 맞췄다.

## 검증과 배포

1. 작업 시작 시 정상본 해시를 확인한다.
2. 원본 문자열과 승인된 참조의 현재 값이 예상값인지 assert한다.
3. 풀의 대상 범위가 비어 있고 용량 안에 있는지 확인한다.
4. 출력 NSO를 다시 해석해 세그먼트 바이트와 헤더 SHA-256을 비교한다.
5. 모든 새 포인터와 명령을 역해석해 예상 글리프 문자열에 도달하는지 확인한다.
6. 정상본과 바이트 단위 diff를 수행한다. 허용된 명령·포인터·새 풀 범위 밖 변경은 실패 처리한다.
7. manifest, 변경 수량, 해시, 미적용 이유를 남기고 복구용 정상본을 로컬 패키지에 넣는다.
8. 실제 게임의 시작·저장 불러오기·메뉴 정렬·전투·조합·상점·의뢰·일기·도움말·음악 감상을 확인한다.

구조 검사 통과와 게임 정상 작동을 별도 상태로 기록한다. 500개 단위 요청이 있어도 근거 있는 후보가 적으면 수량을 채우기 위해 내부 식별자를 번역하지 않는다.

내부 문자열 분류와 공통 영어 제외 정책은 [별도 문서](ayesha-internal-strings.md), 다음 작업의 시작 순서는 [인계 문서](ayesha-next-session.md)를 따른다.
